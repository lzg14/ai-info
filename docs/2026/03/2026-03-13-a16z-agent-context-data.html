a16z：表现不好，可能是缺乏正确的数据上下文

入库 2026-03-13

a16z（Andreessen Horowitz）最近写了一篇深度文章，专门讨论一个很多人正在遇到、但很少有人能说清楚的问题：为什么你的Agent总是表现不稳定？

答案是：不是你设计的prompt不够好，是你给它的上下文不够对。

从"怎么问"到"给什么"

a16z在文章里描述了AI应用开发的一个范式转移。

早期，所有问题都被归结为"prompt engineering"——怎么问、怎么措辞、怎么给例子。大家都在研究各种措辞技巧，试图找到那个magic phrase让模型突然变聪明。

后来大家发现这条路走不通。模型强到一定程度之后，措辞的影响越来越小，真正决定输出质量的变成了：模型在推理的时候，能看到什么信息。

这个转移，从"怎么问"到"给什么"，就是a16z这篇文章的核心。

数据上下文的三个层次

a16z把Agent需要正确处理的数据上下文分成三层：

第一层：任务上下文。 这是最基础的——你要Agent做什么，你需要给它足够的背景信息。一个写代码的Agent，需要知道项目结构、技术栈、代码规范、现有模块。没有这些，它写出来的代码要么风格不统一，要么直接复用不存在的接口。

第二层：会话上下文。 当Agent处理一个多轮任务时，它需要记住之前的对话历史。这不只是简单地把对话记录塞进去，还包括：哪些信息已经被确认过，哪些假设已经被推翻，用户当前的真实意图是什么。

第三层：世界上下文。 最难的一层。Agent需要知道"此时此刻"世界的状态，而不只是训练数据里的世界。比如一个客服Agent需要知道：你的产品库存今天有哪些变化，哪些问题已经被解决过，哪些是新的bug。

为什么给错上下文比不给更危险

a16z在文章里提了一个反直觉的观察：

给Agent错误的上下文，比不给上下文更危险。

因为模型有一个强烈的倾向：它会非常认真地基于你给的信息来回答，即使那个信息是错的、过时的、或者与任务无关的。

它不会说"你给我的背景信息有问题"，它只会老老实实地用错误的前提，推理出一个看起来非常正确、但实际上一文不值的结论。而且这个结论外表上看起来特别自信，特别有道理，特别让你觉得"嗯，模型理解了"。

这就是为什么很多Agent看起来"懂"，实际上在做无用功。

上下文工程的核心原则

a16z总结了上下文工程的几个核心原则：

信号密度原则： 上下文窗口是有限的，每一个token都有成本。你需要在有限的窗口里，塞进去信号最强的信息，同时把噪音挡在外面。这不是简单地把所有信息都塞进去，而是有策略地选择。

时效性原则： 过时的上下文比没有上下文更糟糕。你需要建立一套机制，确保Agent看到的信息是最新的。

分层原则： 不是所有信息都需要放在同一个上下文里。可以通过工具调用、RAG等方式，让Agent在需要的时候主动去获取特定信息，而不是一次性全塞进去。

可调试原则： 当Agent表现不好的时候，你首先应该问的不是"我的prompt哪里不对"，而是"Agent看到了什么信息，这个信息对不对"。

实践中的常见错误

a16z列举了他们在企业级Agent项目中看到的最常见错误：

把整个知识库塞进上下文 → 模型被噪音淹没，抓不住重点。

只给任务描述不给背景 → Agent产出的结果方向正确但细节错误。

用对话历史作为唯一上下文 → 缺少关键确认，Agent基于错误假设继续执行。

从不更新世界上下文 → Agent持续产出基于过时信息的"正确答案"。

核心洞察： Agent时代，真正的工程难点不再是"怎么让模型变聪明"，而是"怎么让模型在正确的时间看到正确的信息"。这是一个数据工程问题，也是一个产品设计问题，但首先是一个思维模式的转变——从优化模型，到优化上下文。
